02 — la linea del tempo

Ogni linguaggio nasce dal problema di quello prima

Non c'è niente da imparare a memoria qui. C'è una sola cosa da vedere: nessun linguaggio è nato perché qualcuno si annoiava. Ognuno risolve un guaio preciso del proprio tempo.

1957
Fortran — scrivere formule matematiche senza fare l'assembly a mano.
1959
COBOL — il gestionale: banche, stipendi. Doveva poterlo leggere anche un contabile. È ancora vivo.
1967
Simula 67 — simulare le navi in un porto: servono cose che si comportano. Qui nascono "classe" e "oggetto".
1970
Pascal — insegnare a programmare in modo ordinato.
1972
C — riscrivere UNIX senza rifare l'assembly per ogni macchina. Nasce la portabilità… del sorgente.
1980
Smalltalk-80 — e se tutto fosse un oggetto che scambia messaggi con gli altri?
1985
C++ — "C con le classi": mettere gli oggetti sopra al C senza perderne la velocità.
1991
Python — leggibilità prima di tutto.
1995
Java, JavaScript, PHP, Ruby — l'anno d'oro. Arriva il Web e servono linguaggi nuovi per starci dentro.
2000
C# — la risposta di Microsoft a Java.
2009 →
Go, Rust, Kotlin, Swift — tanti processori in parallelo, memoria a prova di errore, telefoni.

I tre scalini che ci riguardano

  • Assembly → C. Il problema: il mio programma gira solo su questa macchina. La soluzione: un linguaggio ad alto livello e un compilatore diverso per ogni macchina.
  • C → oggetti. Il problema: quando il programma diventa grande non lo governo più.
  • C → Java. Due problemi insieme: devo ricompilare per ogni piattaforma, e i puntatori mi riempiono il programma di bug.
03 — il problema

Cosa esce davvero dal compilatore

Compilate hello.c come avete sempre fatto. Poi, invece di eseguirlo, guardate che tipo di file è uscito.

gcc hello.c -o hello
file hello
hello: Mach-O 64-bit executable arm64
javac Hello.java
file Hello.class
Hello.class: compiled Java class data,
  version 61.0 ← nessuna architettura

Nel binario C c'è scritto dentro il nome dell'architettura. Su un PC Windows uscirebbe PE32+ x86-64, su Linux ELF 64-bit x86-64. Nel file Java, di architetture, non ce n'è nessuna.

Sei caselle, sei compilazioni, sei file da distribuire.

PE, ELF, Mach-O: cosa sono quelle sigle

Sono i formati di file eseguibile. Un eseguibile non è solo le istruzioni una dopo l'altra: è una scatola con dentro un'etichetta che dice al sistema operativo da dove partire, quanta memoria servirà, quali librerie caricare. Ogni sistema usa la sua scatola, e non sa aprire quelle degli altri.

ELF Executable and Linkable Format La scatola di Linux e di quasi tutti gli Unix — Raspberry Pi e Android compresi. Dal 1988.
PE Portable Executable La scatola di Windows. È quello che c'è davvero dentro un .exe o una .dll.
Mach-O Mach Object La scatola di macOS e iOS.

Quindi il sistema operativo rompe la portabilità anche a parità di processore: cambia la scatola, cambiano le chiamate di sistema, cambiano le librerie. Stessa identica CPU — e un ELF di Linux su Windows non parte, perché Windows quella scatola non la sa aprire.

Aprite le due scatole

Questi sono i file veri della nostra demo: i due sorgenti, e cosa ne ha fatto il compilatore. Guardate soprattutto gli ultimi due.

hello.c sorgente 
#include <stdio.h>

int main(void) {
    printf("Ciao 4A! Sono un programma in C.\n");

#if   defined(__aarch64__)
    printf("  architettura : ARM64\n");
#elif defined(__x86_64__)
    printf("  architettura : x86-64\n");
#endif

#if   defined(_WIN32)
    printf("  sistema      : Windows\n");
#elif defined(__APPLE__)
    printf("  sistema      : macOS\n");
#elif defined(__linux__)
    printf("  sistema      : Linux\n");
#endif

    printf("Lo sapevo gia' da quando mi hanno COMPILATO.\n");
    return 0;
}

// Le righe qui sopra le sceglie il PREPROCESSORE, prima
// della compilazione. Nell'eseguibile finisce UNA SOLA
// di quelle stringhe, e ci resta per sempre.

04 — la mossa

Spostare il lavoro, non farlo sparire

Il file Hello.class non è codice macchina di nessun processore esistente. È il linguaggio macchina di un processore inventato: la Java Virtual Machine. Un computer che non esiste, e che ogni piattaforma vera simula via software.

Se lo aprite con javap -c Hello.class vedete istruzioni tipo getstatic, ldc, invokevirtual. Somiglia all'assembly che avete già visto — ma nessun chip in commercio sa cosa farsene.

Il punto vero, e non è magia

Qualcuno ha comunque dovuto scrivere una JVM diversa per Windows, per Linux, per macOS, per Android. Il lavoro di portabilità non è sparito: è stato fatto una volta sola da chi costruisce la JVM, invece che ogni volta da ogni programmatore.

Si chiama livello di indirezione, e lo ritroverete tutto l'anno: quando un problema si ripete uguale per tutti, lo si risolve una volta in mezzo e lo si toglie a tutti. È lo stesso schema dei driver, di HTTP, dell'alimentatore del portatile.

La controprova: fateli parlare

I due programmi della demo dicono su che macchina stanno girando. Eseguiteli sul Mac della cattedra:

./hello
Ciao 4A! Sono un programma in C.
  architettura : ARM64
  sistema      : macOS
Lo sapevo già da quando mi hanno COMPILATO.
java Hello
Ciao 4A! Sono un programma in Java.
  architettura : aarch64
  sistema      : Mac OS X
  JVM         : 23
L'ho chiesto alla JVM ADESSO, mentre giro.

Sembrano fare la stessa cosa. Non la fanno affatto.

  • Il programma C lo sa perché gliel'ha inciso dentro il preprocessore al momento della compilazione: quelle #if hanno scelto una sola stringa, e nell'eseguibile è finita solo quella. Per sempre. Se lo portate altrove… non parte proprio, quindi la domanda non si pone.
  • Il programma Java non ha niente di scritto dentro: lo chiede alla JVM mentre gira. Copiate lo stesso identico Hello.class su un PC del laboratorio e stamperà x86-64 e Windows 11. Stesso file. Risposta diversa.

Ecco cosa vuol dire davvero quello slogan: il file non sa dove finirà, e non ha bisogno di saperlo. A saperlo è la JVM, che è già lì ad aspettarlo.

"Write Once, Run Anywhere"

Java nasce nel 1991 e non si chiamava Java: si chiamava Oak, e non era per il Web. Doveva far girare software su decoder TV ed elettrodomestici, dove ogni apparecchio aveva un chip diverso — lì la portabilità era vitale. Fu un flop commerciale: quel mercato non decollò.

05 — il colpo di fortuna

Perché nel 1995 quella proprietà diventa oro

Qui la storia gira, e non è perché "il Web andava di moda". È perché il Web presenta, di colpo e a tutto il pianeta, esattamente il problema per cui Java era stato costruito.

Primo motivo: non sai chi c'è dall'altra parte

Il Web del 1995 sono pagine di testo fermo, e Netscape vuole metterci dentro cose che si muovono. Ma chi scrive quel programma ha un guaio nuovo: non ha idea di che computer ci sia dall'altro capo del filo. Chi apre la pagina può arrivare da un PC con Windows 95, da un Mac con processore PowerPC, da una workstation Sun, da una SGI.

Mandargli un eseguibile nativo è fuori discussione: dovresti compilarlo per ogni combinazione esistente, e comunque non sai quale mandargli finché non arriva. Un file di bytecode invece va bene per tutti.

Il Web è il problema dei decoder TV, ma su scala planetaria: tanti apparecchi diversi, un solo programma da consegnare. Oak non era sbagliato. Era arrivato quattro anni presto.

Secondo motivo: la gabbia

E questo di solito ci si dimentica di dirlo, ma pesa quanto il primo. Scaricare ed eseguire il programma di uno sconosciuto è una follia — a meno che qualcosa non lo tenga al guinzaglio.

La JVM controlla il bytecode prima di eseguirlo, e poi decide cosa lasciargli fare: niente accesso al vostro disco, niente connessioni dove gli pare. Si chiama sandbox, il recinto di sabbia. Con il codice nativo non è possibile: una volta partito, fa quello che vuole della vostra macchina.

Quindi la macchina virtuale non serviva solo a tradurre. Serviva anche a contenere. Ed è la ragione per cui è stato pensabile far girare nel browser il codice di un estraneo.

E poi la distribuzione si risolve da sola

Netscape mette la JVM dentro Navigator nel 1996. Nel giro di pochi mesi, praticamente ogni browser del pianeta ha una JVM installata. Il problema di "ma ce l'hanno, la JVM?" sparisce da solo.

Cos'era un'applet

Un piccolo programma Java che viveva dentro una pagina web, in un rettangolo in mezzo al testo. Il browser scaricava il .class dal server e lo faceva girare nella propria JVM.

Aveva una forma strana: l'applet non ha main(). Non parte lei — è il browser a chiamarne i metodi al momento giusto: init() quando la carica, paint() ogni volta che va ridisegnata.

Nel 1996 l'HTML era carta stampata: testo, immagini, link. L'applet era l'unico modo per avere qualcosa di vivo dentro una pagina — animazioni, giochini, grafici di borsa che si aggiornavano, simulazioni di fisica.

Come va a finire

Le applet sono morte, e non "cadute in disuso": Chrome ha tolto il supporto ai plugin nel 2015, Oracle le ha rimosse da Java 11 nel 2018. Oggi non le potreste eseguire nemmeno volendo. Le ha uccise il loro stesso punto di forza — quella gabbia faceva acqua, e il plugin Java è diventato uno dei bersagli più bucati degli anni 2000. Più l'avvio lentissimo, e poi la concorrenza di Flash prima e di JavaScript poi.

Ma Java non è morto affatto — si è spostato dove quella proprietà continua a pagare:

  • Sui server. Sviluppate su Windows o su Mac, mandate in produzione su Linux. Stesso .jar, nessuna ricompilazione. È il pane quotidiano di mezza industria del software, ancora oggi.
  • Su Android. Milioni di telefoni diversi, un'app sola da pubblicare. Di nuovo lo stesso identico problema.

La proprietà è sempre quella del 1991. È cambiato il posto in cui serviva.

E l'idea dell'applet non è morta affatto: scaricare codice di cui non ti fidi ed eseguirlo in una gabbia dentro il browser è esattamente quello che fa JavaScript ogni volta che aprite una pagina — e, ancora più da vicino, quello che fa WebAssembly: bytecode compatto, una macchina virtuale nel browser, sandbox. L'applet rifatta bene trent'anni dopo. Non era l'idea a essere sbagliata: era fragile l'attrezzo.

Ultima cosa, per onestà: i programmatori dell'epoca lo slogan lo storpiavano in "Write Once, Debug Everywhere".

06 — il conto

Non tutto è oro

Ogni scelta di progetto si paga. Queste sono le tre voci del conto.

È più lento a partire

Vero, all'inizio. Poi il JIT (Just-In-Time) compila al volo in vero codice macchina i pezzi che vengono eseguiti più spesso. Oggi Java è vicino al C su molti carichi — ma parte più lento e consuma più memoria.

Serve la JVM installata

Senza JVM il .class è carta straccia. "Run anywhere" vuol dire ovunque ci sia una JVM, non ovunque e basta.

Decidi meno tu

Niente puntatori, niente malloc e free: alla memoria pensa il garbage collector. Comodissimo — ma non scegliete voi quando passa a pulire.

La postilla in caratteri piccoli

Avete visto che file Hello.class stampa una version: 61.0 è Java 17, 67.0 è Java 23. Quel numero è un pavimento. Un .class compilato con JDK 23 su una JVM 17 non parte: muore con UnsupportedClassVersionError.

La compatibilità è all'indietro, non in avanti — esattamente come i file di Word. È il primo errore che incontrerete portando un progetto da casa al laboratorio, quindi lo dico adesso: "Write Once, Run Anywhere", purché la JVM non sia più vecchia di quella con cui avete compilato.

Allora perché non è tutto scritto in Java?

Se Java risolve la portabilità, come mai il kernel di Linux, i videogiochi e il firmware del forno a microonde sono ancora in C? Le ragioni sono più interessanti del semplice "il C è più veloce".

Il kernel: è un problema di circolarità

La JVM, per funzionare, ha bisogno di un sistema operativo sotto di sé: thread, memoria, file glieli deve dare qualcuno. Ma il kernel è quel qualcuno. Non potete far girare il kernel sopra la JVM, perché la JVM ha bisogno del kernel. Il serpente si morde la coda.

E poi il kernel deve fare tre cose che Java, di proposito, non vi lascia fare:

  • Partire quando non c'è ancora niente. All'accensione non esiste nessun runtime da caricare: c'è solo il processore che comincia a leggere istruzioni da un indirizzo.
  • Scrivere a un indirizzo di memoria preciso, quello dove sta il registro di un dispositivo. In Java non esiste il concetto di "indirizzo 0x40021000".
  • Decidere il layout esatto in memoria. "Questa struttura è esattamente questi 8 byte, in quest'ordine", perché è così che la scheda di rete se la aspetta. Java non dà nessuna garanzia su come dispone un oggetto in memoria.

Aggiungete il garbage collector: gestire un interrupt richiede tempi certi, non "appena il GC ha finito di pulire".

I videogiochi: non è la media, è il caso peggiore

Questa è la parte controintuitiva. A 60 fps avete 16,6 millisecondi per disegnare un frame. Se il garbage collector decide di prendersi una pausa di 30 ms, saltate un frame — e il giocatore lo sente. Non conta quanto siete veloci in media: conta non fermarsi mai. Un linguaggio che ogni tanto si prende una pausa a sorpresa, per un gioco, è un problema anche se in media è velocissimo.

Poi c'è la memoria. In C un array di struct sono byte uno attaccato all'altro: il processore li tira su a blocchi e la cache lavora bene. In Java un array di oggetti è un array di riferimenti, e gli oggetti veri stanno sparsi per l'heap. Su centomila particelle da aggiornare a ogni frame, la differenza non la fanno le istruzioni: la fanno i cache miss.

"Ma Minecraft è scritto in Java!"

Verissimo, e infatti la risposta non è "non si può". Si può, e i garbage collector moderni (ZGC, Shenandoah) hanno pause sotto il millisecondo. Il punto è un altro: in C quel controllo ce l'avete per costruzione, in Java dovete combattere contro il runtime per riprendervelo.

Dettaglio che chiude il discorso: la Bedrock Edition di Minecraft — quella per console, telefoni e Switch, dove le risorse sono contate — l'hanno riscritta da zero in C++.

Non esiste il linguaggio migliore. Esiste quello adatto al vincolo che avete. Il vincolo del Web nel 1995 era "non so cosa c'è dall'altra parte". Il vincolo di un gioco è "non devo fermarmi mai". Sono problemi diversi, e vincono linguaggi diversi.

07 — la prossima volta

Quel &s lo scrivete da due anni

Un ultimo passaggio, e poi chiudiamo. In C, per lavorare su uno studente, scrivete una struct e delle funzioni che la ricevono. Guardate bene il primo parametro.

in C — come lo fate ora
typedef struct {
    char  nome[30];
    float media;
} Studente;

void aumentaMedia(Studente *s, float v);

/* e quando la chiamate: */
aumentaMedia(&s, 0.5);
in Java — dalla prossima volta
class Studente {
    private String nome;
    private float  media;

    void aumentaMedia(float v) { ... }
}

// e quando la chiamate:
s.aumentaMedia(0.5);

Non è sparito niente: quel &s si è solo spostato davanti al punto. In Java si chiama this, e non dovete più passarlo a mano perché ci pensa la macchina. Non è una metafora per farvela digerire: è letteralmente quello che succede dentro la JVM, dove l'oggetto su cui chiamate il metodo viene passato come argomento nascosto numero zero.

E allora a cosa serve, oltre a scrivere meno?

  • Niente lega i due nomi, in C. Per il compilatore Studente e aumentaMedia sono due nomi scorrelati che stanno vicini per abitudine vostra. Non potete chiedere "cosa posso fare con uno Studente?": dovete cercare a mano.
  • Il cancello non c'è. Chi include il vostro header può scrivere s.media = -7; e nessuno lo ferma. In Java quella parola è private, e costa una parola.
  • Il nome del tipo lo incollate voi: stampaStudente, stampaDocente, stampaCorso. Il C non ha modo di dire "questa funzione appartiene a quel tipo".

Per la prossima volta

Mezza pagina, si consegna e se ne parla cinque minuti in classe: scegliete un linguaggio del video che oggi non usa quasi più nessuno. Quando è nato, per risolvere quale problema, e perché secondo voi è finito.
